## Text: four engines, one layout

| Backend     | Finds fonts            | Shapes, bidi, breaks                  | Rasterizes                      | Caches                                   |
| ----------- | ---------------------- | ------------------------------------- | ------------------------------- | ---------------------------------------- |
| **X11**     | fc-match, or your files | ntk: fontkit, bidi-js, UAX #14, all JS | ntk, A8, no hinting             | glyph sets on the server, shared by apps |
| **Wayland** | fc-match               | ntk, same as X11                      | ntk, A8                         | a GLES atlas per device                  |
| **Cocoa**   | CoreText               | CoreText                              | CoreGraphics, grayscale AA      | CoreGraphics                             |
| **win32**   | DirectWrite            | DirectWrite                           | Direct2D, ClearType when opaque | DirectWrite                              |

<Card variant="rule" tone="blue" title="One question for layout">

yoga asks a {'<text>'} `measureContent(width)`, memoized per width, rounded up to whole pixels. Every backend answers it.

</Card>
<Card variant="rule" tone="orange" title="Pixels differ, layout must not">

Cocoa answers "narrowest width" with the same UAX #14 package as ntk, so a column wraps at the same words everywhere.

</Card>

<Notes>

Text is where the backends differ most, so it is worth a map. On X11 and Wayland everything is ntk, in JavaScript: fontconfig's fc-match finds the face, a vendored fontkit shapes it, bidi-js orders it, the linebreak package breaks it, and ntk's own rasterizer draws coverage masks with no hinting. X11 keeps those masks on the server as glyph sets; Wayland packs them into a GL texture atlas.

On macOS CoreText does finding, shaping, bidi and wrapping, and CoreGraphics rasterizes with grayscale antialiasing. On Windows DirectWrite and Direct2D do the same jobs, with ClearType where the target is opaque.

The renderer's job is to keep layout identical across that. Yoga only ever asks a text node one thing, how big are you at this width, memoized per width and rounded up to whole pixels so a fractional answer cannot ripple through flexbox.

And one subtle place where engines disagree, the min-content width, which is the width of the longest unbreakable word, Cocoa answers with the same UAX #14 line-breaking package ntk uses, rather than CoreText's breaker. Pixel-level output still differs per backend, and the tests know it.

</Notes>
</Slide>

## Formats, axes, features, colour

<Grid cols={2} gap={20}>
<Card dense title="Formats">

TTF, OTF, TTC, WOFF and WOFF2 wherever ntk draws. WOFF2 through the runtime's own Brotli: 21.4 → 3.9 ms. Gaps: Cocoa's loadFont refuses WOFF2 (#805); win32 wants the bare sfnt.

</Card>
<Card dense title="Variable fonts">

`fontWeight` drives **wght**, fontVariationSettings the rest. **opsz** follows the size: a 13 px SF label gets the Text cut. Cocoa doesn't move wght yet (#806).

</Card>
<Card dense title="Features">

`fontVariantNumeric: 'tabular-nums'`, fontFeatureSettings like ['tnum', 'zero'], and letterSpacing, which drops optional ligatures. #604

</Card>
<Card dense title="Colour and emoji">

COLR and sbix faces draw; a bitmap-only CBDT face is passed by for the next. X11 glyph sets are A8 coverage: one ink colour. CoreText cascades emoji in colour.

</Card>
</Grid>

<Card dense variant="inverse" title="Finding a font is environment, not code">

fc-match follows PATH: on macOS, Homebrew's fontconfig maps sans-serif to Hiragino (#86). A first fallback lookup costs ~110 ms. Ship your faces with <B>loadFont</B> and @fontsource from npm, and every machine draws the same text.

</Card>

<Notes>

What a UI developer can count on. Formats: ntk reads every container a web developer ships, TTF, OTF, collections, WOFF and WOFF2, and decompressing WOFF2 with the runtime's native Brotli made it five times faster. The native backends are behind in places, and those gaps are filed.

Variable fonts are first class on ntk: fontWeight is the weight axis, fontVariationSettings reaches any other axis, and the optical size axis follows the font size automatically, the way browsers do, so small labels in SF get the cut designed for small text. OpenType features are there for UI work: tabular figures for columns of numbers that must not jiggle, slashed zero, stylistic sets, and letter spacing, which turns off optional ligatures as CSS does.

Colour is where X11 is honest about its limits: its glyph sets are alpha masks, so text has one ink colour; a colour bitmap emoji font is skipped for the next face that has the character; CoreText draws emoji in colour.

And the practical advice: system font lookup is an environment fact, slow on first use and different per machine, so an app that cares about its typography ships its faces from npm.

</Notes>

<Card variant="rule" tone="blue" title="Why a UI cares">

Glyphs ≠ characters. Width, caret stops and selection must come from shaped clusters, never from string length.

</Card>
<Card variant="rule" tone="orange" title="Known gaps">

No dictionary breaking for Thai, Lao, Khmer: runs cut at graphemes. No IME on X11 yet (#272).

</Card>

<Notes>

Shaping is the step people forget exists until it breaks. The input is a sequence of Unicode characters, the output a sequence of glyph ids with advances and offsets, and the two are not one to one. A ligature turns two characters into one glyph. Kerning keeps the glyphs but moves them: in Arial at 32 px the T in front of a y advances 17.78 px instead of 19.55. Arabic letters change shape depending on whether they join on either side, and the run is laid out right to left. Devanagari reorders: the short i vowel sign is stored after the consonant but drawn in front of it. Combining marks are positioned onto their base by anchors in the font.

ntk gets all of this from fontkit's script shapers, Arabic, Indic, Hangul and the Universal Shaping Engine, and checked its faster mark lookups against fontkit's own output over 2,113 faces.

For a UI toolkit the consequence is that anything counting characters is wrong: caret positions, hit testing, selection and measurement all have to come from shaped clusters.

The honest gaps: line breaking for scripts without spaces, Thai, Lao, Khmer, needs a dictionary ntk does not have, and there is no input method support on X11 yet. Note the samples on this slide are rendered by the presentation, not by ntk.

</Notes>
</Slide>

## Bidi: one line, two directions

<BidiRows />

<Small>UAX #9 gives each character a level: even runs go left to right, odd runs right to left. Each run is shaped on its own, then reordered.</Small>

<Notes>

Bidirectional text is the other thing a UI toolkit cannot treat as a string. In memory, characters are stored in the order they are typed: Hello, then the Hebrew word shalom starting with shin, then 42. The Unicode bidirectional algorithm, UAX #9, gives every character an embedding level, and runs at odd levels are displayed right to left, so on screen the Hebrew letters appear reversed while the digits and the Latin stay left to right.

ntk runs bidi-js before shaping, shapes each direction run on its own, then reorders the runs for display, and skips the whole thing for text with no right-to-left characters.

For UI the consequences are everywhere. direction rtl on a box mirrors the layout through logical properties. A text's base direction comes from its box rather than guessing from the first strong character; there is no dir auto yet. Arrow keys move the caret logically, toward the start of the text, which is what most native toolkits do; visual caret movement is an open question. A selection that is one range in memory can be several rectangles on screen. Truncation puts the ellipsis at the visual end, the left of an RTL line.

And the bug that shows how deep this goes: bidi-js returns no paragraph for an empty string, so an empty right-to-left field drew its caret on the wrong side until ntk 8.23.

</Notes>

<Notes>

The whole text pipeline on X11 lives in ntk and is pure JavaScript. Matching asks fontconfig's fc-match, or takes a face the app loaded. bidi-js computes the Unicode bidirectional levels and splits the string into direction runs. Each run is split again wherever the primary face lacks a character, using fontconfig's coverage data to pick a fallback.

fontkit, vendored into ntk, shapes each piece: GSUB substitutions such as ligatures and Arabic joining forms, and GPOS positioning such as kerning and mark attachment. Layout breaks lines with UAX #14 and memoizes shaping per word, so a resize re-wraps without reshaping.

Only then does anything reach the server: glyphs it has not seen at this size are rasterized and uploaded once, and every draw after that is a single CompositeGlyphs request.

The output of shaping, shown here for the word Type in Arial at 32 px, is just glyph ids and advances. Notice T's advance: 17.78 instead of its default 19.55, because the font kerns T against y. Offsets dx and dy exist for marks and are rare in UI text.

</Notes>

## Upload once, keep it on the server

<Cols template="1fr 600px" gap={48}>
<Col gap={16}>

One **GlyphSet** per (face, size). `AddGlyphs` for "Type": ids we choose, 0–3, and a GLYPHINFO each:

| glyph  | local id |   w × h |     x, y | xOff: stored advance |
| ------ | -------: | ------: | -------: | -------------------: |
| T (55) |        0 | 20 × 23 |    0, 23 |       **<O>20</O>** |
| y (92) |        1 | 16 × 24 |    0, 17 |       **<O>16</O>** |
| p (83) |        2 | 16 × 24 |   −2, 17 |       **<O>18</O>** |
| e (72) |        3 | 16 × 18 |   −1, 17 |       **<O>18</O>** |

Plus the a8 coverage bitmaps: **1,592 bytes**, sent once. The server now moves its own pen by xOff.

</Col>
<Col gap={18}>

**Ids are ours.** Compact per set, so one byte per glyph until a size has used 256 glyphs.

**Rasterizer:** signed-area accumulation from fontkit outlines, analytic antialiasing. ~25 µs for a 20 px icon.

**Bounded:** 8 MB LRU of uploaded bitmaps; a cold (face, size) is freed with FreeGlyphSet.

**Shared:** ntk apps on one display share glyph sets (\_NTK\_GLYPHD). Each later app skips ~8 ms and ~11.5 KB per face and size.

**Huge sizes** (over 256 px) go as trapezoids: bitmaps grow with size², outlines with √size.

</Col>
</Cols>

<Notes>

This table is the real AddGlyphs request ntk sent for the word Type, captured off the socket. XRender lets the client choose glyph ids, so ntk numbers glyphs 0, 1, 2, 3 per glyph set rather than using the font's own ids (55, 92, 83, 72). That keeps every id under 256 for a typical UI size, which means the 8-bit variant of CompositeGlyphs, one byte per glyph on every draw.

Each GLYPHINFO says how big the bitmap is, where it sits relative to the glyph origin, and xOff: how far the server should move its pen after drawing it. ntk stores the rounded default advance there, so for ordinary text the server walks the pen itself and the client sends nothing per glyph but the id.

Bitmaps come from ntk's own rasterizer over fontkit's outlines, signed-area accumulation as in font-rs and stb_truetype, which gives exact antialiasing with no supersampling. The cache is bounded at 8 MB per connection, and since ntk 8 the glyph sets can be shared between processes on the same display through a small directory protocol, so the second app showing the same UI font rasterizes and uploads nothing.

Very large text, over 256 px, is sent as trapezoids instead, because a cached bitmap costs size squared while an outline costs roughly the square root of the size.

</Notes>
</Slide>

Unkerned text is one elt: 8 bytes, then **1 byte per glyph**. Each kern, mark or drift opens a new elt. A 60-character line costs ~70 bytes.

<Notes>

This is the punchline of the text section, and every byte on it is real: captured from the socket while ntk drew the word Type in Arial at 32 px, and the picture is the server's own output, read back and magnified.

The request header says Render, CompositeGlyphs8, 13 four-byte words. Then the compositing operator, the source picture (a solid black), the destination (the window), no intermediate mask, the glyph set holding Arial at 32 px, and the source origin. Then the glyph list, made of elements. Each element is an 8-byte header (a count, padding, and a pen offset dx, dy) followed by one byte per glyph id, padded to four bytes.

The first element moves the pen to 20, 100 and draws local glyph 0, T. The server then advances the pen by T's stored xOff, 20, to x 40. But the shaped position of y is 17.78 after T, which rounds to 38, because Arial kerns T and y. So the encoder starts a second element with dx minus two, the feff, and lists y, p and e; the server advances by their stored 16 and 18 by itself.

Without the kern this would be a single element and 40 bytes. A typical 60-character line is around 70 bytes after warm-up, and redrawing it never uploads anything again.

</Notes>
