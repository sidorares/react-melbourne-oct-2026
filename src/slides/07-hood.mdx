## The layers, and who decides what

<Col gap={12}>
<Layer name="react">Components, hooks, setState. Knows nothing about output.</Layer>
<Layer name="react-reconciler">Fibers, lanes, the scheduler, diffing, render and commit phases</Layer>
<Layer name="HostConfig" tone="orange">~60 callbacks: create, attach, update, remove. The contract.</Layer>
<Layer name="react-x11 nodes">Retained tree + yoga layout. Decides **how often** drawing happens.</Layer>
<Layer name="ntk">Windows, 2d canvas over XRender, fonts. Decides **how** drawing is encoded.</Layer>
<Layer name="node-x11">The X11 wire protocol in pure JavaScript. No policy.</Layer>
<Layer name="X server" dashed>Local socket, or across the network</Layer>
</Col>

<Notes>

The split of responsibility matters for the second half of the talk. node-x11 is the protocol and nothing else. ntk gives you windows, a canvas-like 2d context over XRender, glyph caches; it owns how a drawing is encoded on the wire. react-x11 owns how often anything is drawn: which nodes changed, which rectangles are stale, when a frame goes out.

The highlighted layer is the only thing a renderer author writes against react-reconciler: the host config.

On macOS and Windows the bottom three layers become a native bridge (@windowkit/appkit, @windowkit/win32); everything from the node tree up is shared.

</Notes>
</Slide>

## A renderer is one function call

<Cols template="1fr 520px" gap={48}>
<Col>

<Code size={26}>

```js
import ReactReconciler from 'react-reconciler';

export const Renderer = ReactReconciler(HostConfig);

// createRoot()
const container = Renderer.createContainer(
  app,           // containerInfo: the ntk App
  ConcurrentRoot,  // lanes, transitions, Suspense
  /* …error handlers */);

// root.render(<App />)
Renderer.updateContainerSync(tree, container, null, cb);
Renderer.flushSyncWork();
```

</Code>

</Col>
<Col gap={28}>

React core never touches output. It calls **your** callbacks.

The container is whatever you want: here, the X connection.

The initial mount is synchronous, so tests can assert straight after `render()`.

</Col>
</Cols>

<Notes>

This is the whole wiring. react-reconciler is a factory: you hand it an object of callbacks and get back a renderer with createContainer, updateContainer and friends. The containerInfo argument is opaque to React; it is handed back to you in appendChildToContainer and friends. react-x11 passes the ntk App, the X connection.

ConcurrentRoot opts into the modern behaviour: lanes, transitions, time slicing, Suspense.

render() uses updateContainerSync + flushSyncWork, so a mount is applied before the call returns; painting is still asynchronous, a frame later. (react-x11 is written against react-reconciler 0.33, React 19.)

</Notes>
</Slide>

## Mounting one tree: the real call order

<Cols template="1fr 1fr" gap={32}>
<Col gap={12}>

<Eyebrow tone="blue">Render phase</Eyebrow>

```js
// beginWork: top-down
getRootHostContext()
getChildHostContext(ctx, 'window')
getChildHostContext(ctx, 'box')
getChildHostContext(ctx, 'text')
// completeWork: bottom-up
createTextInstance('hi')
createInstance('text')
appendInitialChild(text, hi)
finalizeInitialChildren(text)
createInstance('box')
appendInitialChild(box, text)
createInstance('window')
appendInitialChild(window, box)
```

</Col>
<Col gap={12}>

<Eyebrow tone="orange">Commit phase</Eyebrow>

```js
prepareForCommit()
appendChildToContainer(app, window)
  └ attachTopLevel
    └ window.realize()
      CreateWindow, props, child windows
resetAfterCommit()
  └ flushWindowRestacks()
  └ flushWindowMaps()
      MapWindow
// layout pass
commitMount(…) only where
  finalizeInitialChildren
  returned true
```

</Col>
</Cols>

<Notes>

This is issue #4 on one slide. completeWork comes back up the tree, so a renderer that creates windows in createInstance creates the text's window before the box's, and the box's before the window's: bottom-up, with no parent to name yet. That is what the 2015 version did. Now the left column makes no X calls at all, and everything happens on the right.

It is the most useful slide for anyone writing a renderer. beginWork goes down the tree and computes host context for each host element. completeWork comes back up, so the deepest node is created first: the text chunk, then text, then the box, then the window. Each parent is created after its children and immediately given them through appendInitialChild.

By the end of the render phase there is a complete, detached tree of react-x11 nodes, with yoga nodes, and zero X11 requests sent.

The commit then makes exactly one call for the whole thing, appendChildToContainer with the window. react-x11 turns that into realize(), which creates the X window and recurses into child windows. Mapping waits for resetAfterCommit, so a tree of windows appears at once.

commitMount runs later, in the layout pass, only for instances whose finalizeInitialChildren returned true.

</Notes>
</Slide>

# Render computes.<br />Commit touches the world.

## realize(): the window is born in the commit

<Cols template="1fr 640px" gap={40}>
<Col>

```js
realize(parentWindow) { // commit only
  const natural = this._measure();
  attrs.width = natural.width;
  attrs.height = natural.height;
  attrs.parent = parentWindow;
  attrs.backgroundPixel = pixelFor(bg);
  attrs.eventMask |= WINDOW_EVENT_MASK;
  const wnd = app.createWindow(attrs);
  this._attachWindowListeners();
  for (const c of this.children)
    if (c.isWindow) c.realize(wnd);
  this._realizeChildWindows(); // glarea…
  applyWindowStates(wnd, …);
  this._applyTransientFor(…);
  // MapWindow: in resetAfterCommit
}
```

</Col>
<Col gap={22}>

**Lay out first.** An auto-sized window is created at its final size, with no resize jump after mapping.

**Parent at creation.** Top-down, so there's never a ReparentWindow.

**Background pixel.** The server fills newly exposed area with the theme colour, so no white flash on resize.

**State before map.** EWMH state and WM\_TRANSIENT\_FOR are read when the WM frames the window: open fullscreen without flashing.

</Col>
</Cols>

<Notes>

realize() is the fix for #4: the commit-phase walk, top-down. (Backup's "The trap: two appends" shows why it has to walk the subtree itself: React only tells the commit about the root of a new subtree.) It is called from appendChildToContainer for a top-level window, from a mounted parent's insertBefore for a nested one, and from commitMount for a popup.

Order matters at every step. Layout runs before CreateWindow, so a window whose size is auto is born the right size; doing it afterwards means a window mapped at a default size and corrected a frame later. The parent is known at creation because realization is top-down.

The background pixel is what X paints into newly exposed area before the app has drawn it, so setting it to the colour about to be painted makes a resize flash invisible.

And window-manager state (fullscreen, maximized, transient-for, decorations, XDND awareness) is written before the map, because an unmapped window declares its initial state while a mapped one has to ask. Mapping itself is deferred to resetAfterCommit so a tree of windows appears at once.

</Notes>
</Slide>

## Four elements are windows; the rest is painted

    <tr><td><O>{'<glarea>'}</O></td><td>child window on a GLX visual</td><td>commit, with its window</td></tr>
    <tr><td><O>{'<foreign>'}</O></td><td>another process's window, over XEmbed</td><td>commit: reparent into a socket</td></tr>
    <tr className="hl-blue"><td><B>{'<box> <text> <image> <canvas> …'}</B></td><td>one JS node + one yoga node, drawn into the owning window's back buffer</td><td>render: a constructor, nothing more</td></tr>
  </tbody>
</table>

A form with 300 controls is one X window. Clicks reach a {'<box>'} by hit testing the node tree, with capture and bubble like the DOM.

<Notes>

Decision two from the July slide, and the architectural decision everything else follows from. Early X toolkits made every widget a window; react-x11 does not. Only four elements map to real windows of the display system: window and popup because they are what the window manager deals with, glarea because OpenGL needs its own drawable, and foreign because the window belongs to another process.

Everything else is a lightweight retained node with one yoga layout node, painted into the owning window's double-buffered 2d context. That is why the rest of the talk is about damage: with one surface per window, the renderer, not the X server, decides what to repaint, and it can decide very precisely.

It is also why events are synthetic: X only knows that the pointer is in the window, so react-x11 hit-tests its own tree front to back and dispatches capture and bubble phases itself.

</Notes>

<Notes>

Follow the counter we just built. The X server sends a ButtonPress, a 32-byte event. node-x11 decodes it; ntk's Window object emits mousedown (and coalesces motion to one per frame). react-x11's EventManager subscribes to each window once, never per element, and reads handlers from node.props at dispatch time, so a handler is never stale. It hit-tests the retained node tree front to back, in paint order, and dispatches a synthetic event with capture and bubble phases.

The handler runs inside runWithPriority(Discrete), so setN lands on SyncLane. The dispatcher's discrete wrapper then calls flushSyncWork, which renders and commits immediately: the text chunk gets commitTextUpdate, nodes whose parents re-rendered get commitUpdate and therefore applyProps. Changed nodes call invalidate, which records a damage rect on the owning window.

Then flushPendingFrames paints right away if the server has shown the previous frame: layout, paint into ntk's back buffer, and present by copying only the damaged rects. All of that happens before the event handler returns.

Bridge to the next section: that is one click, and it is cheap. Now do it 120 times a second, with a million rows, over ssh.

</Notes>
